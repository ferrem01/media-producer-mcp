# Unified Codegen Architecture -- Full Spec

**Status:** Proposed
**Date:** 2026-06-14
**Author:** Ed (with Marc)
**Replaces:** Refactors 2, 3, and 4

## Summary

Replace the current 5-pipeline architecture with a single codegen pipeline. Every scene goes through the LLM. The LLM outputs `.scene.html` files that can embed library components via `<component>` tags. Sequences, templates, and the library-only path all collapse into "codegen that uses `<component>` tags."

## File Extension Convention

- `.component.html` = reusable building block (library or tenant-defined)
- `.scene.html` = generated scene composition (codegen output, may embed components via `<component>` tags)

Both use the same internal structure (`<template>` + `<style>` + `<script>`) and are parsed the same way by the assembler. The extension communicates intent: components are reusable, scenes are compositions.

## Core Principles

1. **Everything is codegen.** Every scene is generated by the LLM as a `.scene.html` file. No separate paths for library, template, freeform, custom, or sequence scenes.

2. **`<component>` tags are how you reuse.** The LLM embeds library components with `<component type="..." data='...' />` tags instead of rewriting them from scratch. The assembler resolves these to real component HTML/CSS/JS at build time.

3. **Choreography is code.** Component visibility, enter/exit/move animations, and beat timing are GSAP code written by the LLM. No separate `beats[]` or `choreography[]` data structures.

4. **One pipeline, one assembler, one scene type.** The scene model becomes a thin wrapper: id, label, duration, transition, source file, voiceover text.

## `<component>` Tag Spec

### Syntax

```html
<component type="quotient-chat" data='{
  "conversation_title": "Canva Campaign",
  "messages": [
    { "role": "user", "text": "Create a LinkedIn post" },
    { "role": "agent", "text": "Connecting to Canva..." }
  ],
  "mode": "panel"
}' />
```

### Attributes

| Attribute | Required | Description |
|-----------|----------|-------------|
| `type` | Yes | Component type name from the library catalog |
| `data` | No | JSON string of data props (bound to component template) |
| `id` | No | Instance id (auto-generated if omitted: `comp_0`, `comp_1`, ...) |
| `class` | No | Additional CSS classes on the wrapper |
| `style` | No | Inline styles on the wrapper |

### Resolution (what the assembler does)

1. **Find** -- looks up `type` in the component library (global, tenant, project)
2. **Parse** -- extracts `<template>`, `<style>`, `<script>` from the `.component.html` file
3. **Bind** -- applies `data` JSON to template bindings (`{{variable}}`, `data-bind`)
4. **Scope** -- prefixes CSS selectors with a unique instance scope (e.g., `[data-comp-id="comp_0"]`)
5. **Replace** -- replaces the `<component>` tag with:
   ```html
   <div class="component-instance" data-comp-id="comp_0" data-comp-type="quotient-chat">
     <!-- parsed + bound template HTML -->
   </div>
   ```
6. **Collect CSS** -- appends scoped CSS to the document's style block
7. **Collect JS** -- registers the component's `createTimeline` function, called during timeline setup:
   ```javascript
   // Auto-generated by assembler
   (function() {
     var el = document.querySelector('[data-comp-id="comp_0"]');
     var data = { /* parsed data props */ };
     var compTl = createTimeline_comp_0(el, data, ctx);
     masterTimeline.add(compTl, 0);  // or at a label specified by the scene's own timeline
   })();
   ```

### Timeline Integration

The scene's own `createTimeline` function returns a master timeline. Component timelines are registered as available sub-timelines. The scene code can:

- Let components auto-play from t=0 (default)
- Add component timelines at specific positions: `tl.add(ctx.getComponentTimeline('comp_0'), 8)`
- Control component visibility with GSAP: `tl.fromTo('[data-comp-id="comp_0"]', { opacity: 0 }, { opacity: 1 })`

```javascript
function createTimeline(el, data, ctx) {
  const tl = gsap.timeline();
  
  // Hide all components initially
  gsap.set('[data-comp-type]', { opacity: 0 });
  
  // Beat 1: show chat at t=0
  tl.to('[data-comp-id="comp_0"]', { opacity: 1, duration: 0.6 });
  tl.add(ctx.getComponentTimeline('comp_0'), '<');
  
  // Beat 2: slide chat left, show canva at t=8
  tl.to('[data-comp-id="comp_0"]', { x: '-30%', width: '45%', duration: 0.8 }, 8);
  tl.to('[data-comp-id="comp_1"]', { opacity: 1, duration: 0.8 }, 8);
  tl.add(ctx.getComponentTimeline('comp_1'), 8);
  
  return tl;
}
```

The `ctx` object provides:
- `ctx.getComponentTimeline(id)` -- returns the component's GSAP timeline
- `ctx.duration` -- scene duration in seconds
- `ctx.fps` -- frame rate
- `ctx.canvas` -- { width, height }
- `ctx.brandKit` -- brand colors, fonts, etc.

## Pipeline (new)

### Generate Flow

```
User prompt
  → 1. Prompt Expansion (expander.ts)
  → 2. Creative Direction (concept-director.ts)
  → 3. Storyboard Planning (unified-planner.ts)
       Output: StoryboardResult with scene briefs
       Saved to: project.storyboard (NEW -- planning context preserved)
  → 4. Media Enrichment (images, stock footage)
  → 5. Scene Codegen (for each scene, in parallel)
       LLM receives: scene brief, component catalog with schemas,
                     creative bible, brand kit, reference images
       LLM outputs: .scene.html with <component> tags + custom code
       Assembler resolves <component> tags at render time
  → 6. Critique (vision-based review of rendered frames)
  → 7. Audio (TTS voiceover, music, mixing)
  → 8. Save project.json
```

### Mode Behavior (Refactor 4)

Same pipeline, mode controls where to stop:

| Mode | Steps | Output |
|------|-------|--------|
| `plan` | 1-3 | project.json with storyboard, status: "planned" |
| `generate` | 4-8 (from saved storyboard) | project.json with scenes + render, status: "complete" |
| `full` | 1-8 | everything in one shot |

All three modes use the same code path. `full` is literally `plan` + `generate` in sequence.

### Storyboard (saved to project.json)

```typescript
interface Storyboard {
  name: string;
  creative_bible: CreativeBible;
  scenes: StoryboardScene[];
}

interface StoryboardScene {
  label: string;
  duration_seconds: number;
  brief: string;                    // what the scene should show/communicate
  transition_in?: { type: string; duration_seconds: number };
  voiceover_text?: string;
  suggested_components?: string[];  // component types the planner recommends
  hero_image?: string;
}
```

The planner outputs briefs, not implementation details. It doesn't decide template vs freeform vs library -- codegen makes those decisions. The planner suggests components but codegen can use them, modify the approach, or go fully custom.

## Assembler (new)

One assembler replaces `scene-assembler.ts`, `sequence-assembler.ts`, and `composite-assembler.ts` for scene building.

### Input
- Scene `.component.html` source (codegen output)
- Component library sources (for `<component>` tag resolution)
- Brand kit
- Canvas config

### Process
1. Parse the scene `.component.html` (template + style + script)
2. Find all `<component>` tags in the template
3. For each `<component>` tag:
   a. Load the library component source
   b. Parse it (template + style + script)
   c. Bind data from the `data` attribute
   d. Scope CSS with unique prefix
   e. Replace the tag with the rendered component HTML
   f. Register the component's timeline function
4. Inject brand CSS variables
5. Inject GSAP from local files
6. Build the master script:
   - Scene's `createTimeline` function
   - All component `createTimeline` functions (renamed to avoid collisions)
   - `ctx` object with `getComponentTimeline()` helper
   - `window.__MP_TIMELINE` and `window.__MP_READY` for capture
7. Output self-contained HTML document

### Output
Self-contained HTML file ready for Playwright capture. Same as today's assembler output.

- Add tag parsing to the assembler
- Component resolution, data binding, CSS scoping, timeline wiring
- Test with manually-written scenes that use `<component>` tags
- **No LLM changes yet** -- just the assembler capability

- Update the freeform-agentic generator to output `<component>` tags
- Update the prompt to include component catalog with schemas

- Simplify Scene type (remove components[], beats[], choreography[])
- Add project.storyboard (preserve planning context)

- `full` = `plan` + `generate` using same code path

## Risks

1. **Every scene hits the LLM.** Simple scenes that today are just data binding will now go through codegen. Mitigated by: small prompts for simple scenes, component tags make the LLM's job trivial.

2. **Big assembler change.** The `<component>` tag resolution is the hardest part. CSS scoping collisions, timeline wiring, nested components. Needs thorough testing.

3. **Migration period.** Old and new pipelines running in parallel during phases 2-4. Both need to work. Test coverage matters.

4. **LLM quality variance.** Today library components are deterministic. With codegen, even "simple" scenes have LLM variance. Mitigated by: critique loop catches bad output, component tags ensure the core visuals are consistent.

---

## Success Criteria

- One pipeline, one scene type, one assembler
- `<component>` tags resolve correctly with scoped CSS and wired timelines
- A 30-second multi-component scene renders correctly via codegen + component tags
- `mode: "plan"` and `mode: "full"` use the same code path
- Storyboard preserved in project.json
- No regression in render quality for existing scene types
