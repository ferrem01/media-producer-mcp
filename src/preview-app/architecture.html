Media Producer MCP

Architecture, pipelines, and concepts

System Overview

Media Producer MCP is an AI-powered video/image production server. It takes a text prompt, plans a storyboard, generates or selects visual components, assembles them into HTML+GSAP scenes, captures frames via Playwright, and encodes the final video with ffmpeg.

MCP Protocol

Generate Pipeline

The generate pipeline transforms a user prompt into a complete project with scenes, components, and timing. It runs as a queued background job.

1. Prompt Expansion expander.ts
Detects thin prompts and expands them into rich creative briefs. Rich prompts pass through unchanged. Ensures the planner always has enough detail to work with.
2. Creative Direction concept-director.ts
Generates 3 distinct creative concepts, self-critiques them, picks the strongest. Outputs a "creative bible" with the big idea, storytelling pattern, visual through-line, emotional arc, and key visual commitments.

✅ Refactor 1 complete: CreativeBible is now passed as structured data through the entire pipeline (planner, scene generator, custom codegen, freeform). Saved to project.creative_bible in project.json. Previously it was flattened to prose text and lost after the planner.
3. Storyboard Planning unified-planner.ts
Plans the full storyboard: decides each scene's type (library component, template, custom freeform, or sequence), assigns components, writes briefs, and sets timing. The planner has 5 options per scene and a component catalog to reference.
3a. Sequence Conversion sequence-converter.ts
Post-planner pass: detects when multiple consecutive scenes reference the same component types and merges them into a single sequence scene with choreographed beats. Only fires when the planner didn't already output a sequence.
4. Scene Generation scene-generator.ts
Per-scene generation. Library components pass through with data binding. Custom/freeform scenes get full HTML+GSAP generated by the LLM (via component-gen.ts or freeform-agentic.ts). Sequences carry through beats and choreography.

✅ Refactor 1: Custom component and freeform generators now receive the CreativeBible and inject visual style constraints (colorMood, motionPersonality, spatialStrategy) directly into their LLM prompts.
5. Visual Critique critiquer.ts / multi-pass-critiquer.ts
Renders a preview frame of each scene, sends it to a vision model for evaluation. Scores the scene and suggests revisions. Multi-pass critique uses contact sheets (6 frames across the timeline) for motion evaluation. Scenes below threshold get revised.
6. Media Enrichment media-enrichment.ts / image-enrichment.ts
Enriches scenes with stock footage (Pexels API), AI-generated images (DALL-E/others), and asset references. Replaces placeholder images with real content.
7. Audio Generation scene-voiceover.ts / music.ts
Generates TTS voiceover per scene from voiceover_text. Selects background music. Builds audio mix with ducking (voice up, music down during speech).
8. Save Project persistence/project.ts
Writes project.json with all scenes, components, timing, audio tracks, and metadata. The project is now ready for the render pipeline.

Where Data Lives in project.json

This is a key source of confusion. The storyboard from the unified planner is NOT stored separately -- it gets dissolved into project.scenes[] after generation. The planning context (why each scene was chosen, creative decisions) disappears.

├── project_id, tenant_id, name, format, status
├── canvas: { width, height, fps }
├── brand_kit: { colors, fonts, logos }

│     └── prompt, target, duration...

│     └── estimated_duration

│     └── visualStyle: { colorMood, typography, motion, spatial }

⚠️ Data Loss Point

When mode:"full" runs, the StoryboardResult from the unified planner is never saved. Each PlannedScene goes through generateScene() and becomes a Scene in project.scenes[]. The planning context -- why each scene was chosen, which pipeline path was selected, the creative rationale -- is lost.

The creative_bible is now preserved (Refactor 1), but the storyboard itself is not.

🔧 Refactor 4: Unify Generate Modes

mode:"full" should not be a separate code path. It should run plan → generate → render using the exact same pipeline. One PlannedScene type. Storyboard always saved. The mode just controls where to stop:

  • plan: stop after planning, save storyboard
  • generate: pick up from saved storyboard, generate + render
  • full: run everything end-to-end, same code path

Status: Planned refactor. See ARCHITECTURE.md roadmap.

💡 Two Different PlannedScene Types

Confusingly, there are TWO PlannedScene interfaces:

  • types.ts PlannedScene -- used by the plan mode (script writer). Has purpose, template suggestion, asset needs.
  • unified-planner.ts PlannedScene -- used by the full mode (storyboard planner). Has components[], freeform_brief, beats[], choreography[].

Same name, different shapes, different files. The plan mode and full mode are effectively two separate planning systems.

Render Pipeline

The render pipeline takes a saved project.json and produces the final output file (MP4, GIF, PNG, or PDF). It runs as a queued background job with parallel scene rendering.

1. Scene Assembly scene-assembler.ts / sequence-assembler.ts
Each scene's components are assembled into a self-contained HTML document. Brand kit becomes CSS variables, components are positioned and layered, GSAP scripts build a master timeline.

Standard scenes use scene-assembler.ts: all component timelines start at t=0.
Sequence scenes use sequence-assembler.ts: components are placed on a shared stage, a master timeline has labeled beats, components enter/exit/move at choreographed times.
2. Frame Capture capture.ts / capture-worker.ts
Playwright loads the assembled HTML, steps through the GSAP timeline frame-by-frame (at the project FPS), and screenshots each frame as PNG. Runs in a worker process. Scenes render in parallel (concurrency: 2).
3. Scene Encoding encode.ts
ffmpeg encodes each scene's frames into an MP4 segment (H.264). Quality settings, resolution, and frame rate come from the project canvas.
4. Transitions transitions.ts
Between-scene transitions are rendered as mini HTML scenes. Extract last frame of scene A and first frame of scene B, composite them with a GSAP animation (crossfade, slide, zoom, shader effects), capture, and encode.

30+ transition types including WebGL shader transitions (crosswarp, ripple, radial, chromatic).
5. Concatenation encode.ts
ffmpeg concatenates all scene segments and transition segments into one continuous video. The concat filter handles different durations seamlessly.
6. Audio Mix mixer.ts
Mixes voiceover, music, and SFX tracks onto the video. Applies ducking (music volume drops during speech) and fade in/out. Outputs the final output.mp4.

Scenes vs Sequences

The two core composition models. Scenes are the building block; sequences extend scenes with multi-beat choreography.

🎞️ Scene (Standard)

A single visual moment. One set of components, all animated simultaneously from t=0.

  • Components layered by z-index
  • All timelines start together
  • Typically 3-8 seconds
  • Connected by between-scene transitions
scene-assembler.ts

🎬 Sequence

A multi-beat continuous take. Components persist across beats, entering and exiting the shared stage at choreographed times.

  • Shared stage with all components
  • Master GSAP timeline with labeled beats
  • Components enter/exit/move per beat
  • Typically 20-40 seconds
  • No cuts between beats (single take)
sequence-assembler.ts

How a Sequence Works

A sequence is a scene with beats[] and optional choreography[]. The assembler places all components on stage (hidden), then reveals/moves/hides them at each beat boundary.

Sequence Data Flow

📝 Planner Output

The unified planner outputs a scene with beats[] (label, brief, duration, voiceover) and choreography[] (startTime, duration, visibleComponents, transitions).

🔄 Sequence Converter

Fallback: if the planner outputs separate scenes that should be a sequence, the converter detects consecutive component-eligible scenes and merges them into one sequence with auto-generated choreography.

🏗️ Sequence Assembler

Builds the final HTML. Places all components on a shared stage (hidden). Generates a GSAP master timeline with beat labels. At each beat: show/hide components, trigger enter/exit/move transitions, start component-internal animations.

Component Library

67 reusable HTML+CSS+GSAP animation components. Each is a self-contained .component.html file with a template section (HTML), style section (CSS), and script section (JS with createTimeline function). Components are data-driven via template binding.

Component Anatomy

📦 .component.html

Three sections in one file:

  • <template> -- HTML structure with {{variable}} bindings
  • <style> -- Scoped CSS (auto-prefixed per instance)
  • <script> -- createTimeline(el, data, ctx) returns a GSAP timeline

The assembler parses these, binds data, scopes styles, and wires timelines into the master GSAP timeline.

Scene Creation Pipelines

The planner decides HOW each scene is built. There are 5 distinct paths through the system, each with different tradeoffs between quality, speed, and creative control.

🧠 How the Planner Decides

For each scene, the unified planner (unified-planner.ts) picks one of 5 options based on the narrative moment, available components, and the creativity parameter (0-1). The scene generator (scene-generator.ts) then routes to the appropriate pipeline.

scene-generator.ts routing:
  if (planned.freeform && planned.beats) → Sequence Pipeline
  if (planned.freeform) → Freeform Pipeline
  if (planned.template) → Template Pipeline
  if (comp.custom) → Custom Component Pipeline
  else → Library Component Pipeline

Uses pre-built components from the 67-component library. No LLM generation needed for visuals. Fastest path.

Data Model

Projects are stored as JSON with associated file assets on disk. Multi-tenant architecture with tenant isolation.

File Structure

/data/media-producer/
  └── {tenant-id}/
      ├── brand-kit/
      │   ├── brand-kit.json
      │   └── assets/ (logos, fonts)
      ├── components/ (tenant-specific components)
      └── projects/
          └── proj_{id}/
              ├── project.json
              ├── components/ (freeform HTML files)
              ├── _work/
              │   ├── scene_0/ (frames, scene.html, scene.mp4)
              │   ├── scene_1/
              │   ├── transition_0_1/
              │   └── ...
              └── output/
                  └── output.mp4

Project JSON Shape

📋 Project

  • project_id -- unique identifier
  • tenant_id -- tenant isolation
  • name -- display name
  • format -- video | image | gif | presentation
  • canvas -- width, height, fps, preset, background
  • brand_kit -- colors, fonts, logos
  • scenes[] -- ordered scene list
  • audio -- track list + ducking config

🎞️ Scene

  • id -- scene identifier
  • label -- display name
  • duration_seconds
  • components[] -- positioned components
  • transition_in -- entry transition
  • beats[] -- (sequences only)
  • choreography[] -- (sequences only)
  • background -- color or gradient
  • voiceover_text

🧩 SceneComponent

  • id -- instance id (comp_0, comp_1...)
  • type -- component type name
  • data -- template binding data
  • z_index -- layer order
  • position -- x, y, width, height (%)

🎵 SequenceBeat

  • label -- beat name
  • brief -- what happens
  • duration_seconds
  • voiceover_text

💃 Choreography

  • label -- matches beat label
  • startTime -- seconds (cumulative)
  • duration -- seconds
  • visibleComponents[] -- component ids
  • transitions -- enter/exit/move per component
  • positions -- position overrides

🎨 BrandKit

  • colors -- primary, accent, background, text
  • fonts -- heading, body (Google Fonts)
  • logos -- primary, secondary, icon
  • name -- brand name
